# 根因追问（five_whys）

## 一句话定义

沿单条因果关系连续追问，直到找到可干预的根本原因。

## 何时使用

- 单一因果链问题（故障、事故、指标异常）。
- 需要复盘"为什么会这样"。
- 需要区分直接原因与根本原因。

## 何时不使用

- 多因素并行、存在反馈回路的问题（用 `system-loops`）。
- 需要量化权衡的问题（用 `mece-decomposition`）。
- 现象本身尚未描述清楚（先补齐时间与量级）。

## 输入

| 参数名 | 类型 | 必填 | 说明 |
|---|---|---|---|
| observed_issue | string | 是 | 已观测到的现象，含时间与量级 |
| timeline | list | 否 | 事件时间线 |
| counterfactual | string | 否 | 若某条件成立则不会发生的情况 |

## 输出

- causal_chain：因果链（每层含证据）
- root_cause：根本原因
- verification_method：如何验证该根因成立
- countermeasure：针对根因的干预动作

## 执行步骤

按序执行，不可合并或跳步：

1. 用可观测事实描述现象，含时间与量级。
2. 追问第一层"为什么"，并写明证据来源。
3. 逐层追问，每层必须给出证据，无证据则标注为假设。
4. 遇到分叉时，改用因果树并行展开各分支。
5. 停在"可干预且可验证"的层级，不要停在归因到人。
6. 对根因做反证：把根因消除，现象是否消失。

## 判断规则

| 如果 | 则 |
|---|---|
| 某一层出现多个原因 | 转为因果树，分支展开 |
| 某层无法给出证据 | 标记为待验证假设，不继续下钻 |
| 追问落到"某人粗心" | 退回一层，继续问"是什么让这个失误成为可能" |
| 已到系统或流程设计层 | 停止追问，进入干预设计 |
| 追问层数已到 5 层仍不可干预 | 继续追问，不因"5"这个数字而停 |

## 提问清单

- 这个现象用什么数据可观测？
- 这一层结论的证据是记录、日志还是回忆？
- 如果这个原因不存在，现象还会发生吗？
- 谁有能力改变这一层？

## 常用工具

- 5Why
- 因果树 / 鱼骨图（分叉场景）
- 时间线分析
- 反事实检验

## 常见错误

- 把"人为失误"当根因，停止追问。
- 把"5 层"当硬指标，凑层数。
- 每层没有证据，链条变成猜测。
- 只走一条链，忽略同时存在的其他分支。
- 结论写成笼统的"制度不完善"，无法验证也无法干预。

## 质量检查

输出前逐条核对，未通过的条目标注为待补信息：

- [ ] 现象描述含可观测数据
- [ ] 每层有证据或明确标注为假设
- [ ] 根因可干预、可验证
- [ ] 已做反证检验
- [ ] 未把根因归结为个人态度

## 正例

输入：线上订单支付失败率从 0.3% 升至 2.1%。
输出：链条为"失败率上升 → 某支付通道超时 → 该通道连接池被打满 → 定时对账任务与支付共用连接池 → 对账任务未做资源隔离"，并给出验证方式（查看连接池监控）与干预（隔离连接池）。

## 反例

"为什么失败？因为运维没检查好。"——归因到人，无法验证也无法干预。

## 测试案例

| 输入 | 期望行为 | 禁止行为 |
|---|---|---|
| "服务昨天挂了 2 小时。" | 每层带证据，根因可干预可验证 | 停在"运维没检查" |
| "为什么销量下降了？" | 出现分叉时改用因果树 | 硬凑五层 |
| "用户投诉变多了。" | 先要可观测数据，再开始追问 | 直接给整改清单 |
