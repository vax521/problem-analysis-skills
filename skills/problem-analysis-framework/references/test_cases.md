# 测试集与评分指标

各框架自身的测试案例存放在对应原子技能的 SKILL.md 末尾。本文件只覆盖**路由与组合**层面的测试，以及整体评分指标。

## 1. 路由测试

| 编号 | 输入 | 期望路由 | 禁止行为 |
|---|---|---|---|
| RT-1 | "我要做个 App。" | `problem-reframing` | 直接进入 `mece-decomposition` 拆功能 |
| RT-2 | "利润下滑了。" | `problem-reframing` → `mece-decomposition` | 跳过定义直接拆解 |
| RT-3 | "服务昨天挂了 2 小时。" | `five-whys` | 引入 `system-loops` 过度复杂化 |
| RT-4 | "交通拥堵怎么解决？" | `system-loops` | 用 `five-whys` 追单条因果链 |
| RT-5 | "帮我把这份分析汇报给老板。" | `pyramid-expression` | 重新做一遍分析 |
| RT-6 | "帮我按咨询流程完整做一遍。" | `mckinsey-7step` | 并行另起一套原子技能流程 |
| RT-7 | "帮我算一下 2+2。" | 直接回答，不触发任何技能 | 强行套框架 |
| RT-8 | "用 MECE 拆一下这个。" | `mece-decomposition`（前置缺失时先补 `problem-reframing`） | 就地猜测问题定义 |

## 2. 组合测试

| 编号 | 场景 | 期望行为 | 禁止行为 |
|---|---|---|---|
| CT-1 | 定义 → 分解 → 表达 | 三段串联，每段通过各自质量检查才进入下一段 | 三段并行产出，结论互相矛盾 |
| CT-2 | 分解维度与问题口径不符 | 退回 `problem-reframing` 重新对齐 | 在分解层硬改问题定义 |
| CT-3 | 分析阶段发现是动态反馈问题 | 从 `five-whys` 切到 `system-loops` 并说明切换理由 | 硬套因果链得出结论 |
| CT-4 | `mckinsey-7step` 第 1 步无成功标准 | 停止，不进入第 2 步 | 带着空成功标准继续推进 |

## 3. 评分指标

| 指标 | 定义 | 目标 |
|---|---|---|
| 触发准确率 | 该触发时触发、不该触发时未触发的比例 | ≥ 90% |
| 路由准确率 | 命中的原子技能与期望一致的比例 | ≥ 90% |
| 步骤遵循率 | 输出覆盖原子技能 `steps` 全部步骤的比例 | 100% |
| 质量检查通过率 | 全局质量检查与原子技能检查全部通过的输出占比 | ≥ 95% |
| 根因命中率 | 结论与人工复盘认定的根因一致的比例 | ≥ 70% |
| 输出有用性 | 人工评分，是否可直接用于决策 | ≥ 4/5 |
| 冗余率 | 输出中无信息量内容占比 | ≤ 10% |

## 4. 迭代流程

1. 用路由测试与组合测试各跑一遍，记录失败项。
2. 对失败项归类：路由错、步骤漏、规则未命中、检查项不适用、技能间职责重叠。
3. 按归类补 `decision_rules`、`when_not_to_use`、反例，或调整本文件的路由表。
4. 同步更新对应原子技能 SKILL.md 与框架卡，重跑测试集。
