# MECE 分解与优先级排序（mece_decomposition）

## 一句话定义

用不重叠、不遗漏的方式把问题切成可独立分析的子问题，再对子问题排序找杠杆点。

## 何时使用

- 问题复杂、涉及多个变量。
- 需要量化或对比（利润下滑、增长停滞、成本超支）。
- 需要给出一份可分工的分析计划。

## 何时不使用

- 问题尚未定义清楚（先走 `problem-reframing`）。
- 单一因果链的线性问题（用 `five-whys` 更省成本）。
- 多因素动态反馈问题（用 `system-loops`）。

## 前置条件

必须有已通过质量检查的问题陈述。若缺失，先调用 `problem-reframing` 并停下，不要在本技能内顺手定义问题。

## 输入

| 参数名 | 类型 | 必填 | 说明 |
|---|---|---|---|
| problem_statement | string | 是 | 已澄清的问题陈述 |
| decomposition_axis | string | 否 | 分解维度，默认按公式或流程 |
| available_data | list | 否 | 可用于验证的数据 |

## 输出

- logic_tree：逻辑树（含层级与分解依据）
- mece_check：每层是否满足不重叠、不遗漏的判定
- prioritized_issues：排序后的子问题
- analysis_plan：每个子问题的验证方式与所需数据

## 执行步骤

按序执行，不可合并或跳步：

1. 确定分解维度（公式法、流程法、结构法、二分法）。
2. 先做一层分解，检查是否 MECE。
3. 对每个子问题追加下一层，直到可直接验证为止。
4. 用 ICE 对子问题排序（Impact 影响面 × Confidence 可验证性 × Ease 取证难度）。
5. 只保留排序前 20% 的子问题进入分析。
6. 为保留项写出验证方式与数据需求。

## 判断规则

| 如果 | 则 |
|---|---|
| 子项之间存在交叉 | 重新选择分解维度，不要在同一层混用两种维度 |
| 子项之和覆盖不了上层 | 补充分类或改用二分法（是 / 否） |
| 某子项无法验证 | 继续下钻，直到落到可观测指标 |
| 子项超过 7 个 | 合并或改用两层结构 |
| 某子项数据不可得 | 在排序阶段排除，不进入分析计划 |

## 提问清单

- 这一层的分解依据是同一个吗？
- 是否存在同时属于两个子项的案例？
- 把所有子项相加，能还原上层问题吗？
- 哪个子项一旦改善，整体改善最明显？

## 常用工具

- 逻辑树 / 议题树
- 公式分解（利润 = 收入 − 成本，收入 = 客单价 × 客户数 × 复购率）
- 3C（Company / Customer / Competitor）
- 波特五力、7S（组织诊断场景）
- ICE 打分表

## 常见错误

- 同层混用维度，导致重叠。
- 树只长一层就下结论，子问题仍不可验证。
- 把 ICE 当成精确计算，忽略 Confidence 权重。
- 分解维度选了不可获取数据的维度。
- 对所有子问题平均用力，不做取舍。

## 质量检查

输出前逐条核对，未通过的条目标注为待补信息：

- [ ] 每层分解依据统一
- [ ] 满足不重叠、不遗漏
- [ ] 叶子节点可直接验证
- [ ] 已排序并明确保留项
- [ ] 每个保留项有数据获取路径

## 正例

输入：利润下滑。
输出：第一层拆为"收入 ↓"与"成本 ↑"；收入层拆为"客单价 × 客户数 × 复购率"；经 ICE 排序保留"复购率"与"获客成本"两项，并给出取数口径。

## 反例

把第一层拆成"收入、成本、竞品动作、市场环境"——竞品动作不属于同一分解维度，且与收入成本交叉。

## 测试案例

| 输入 | 期望行为 | 禁止行为 |
|---|---|---|
| "利润下滑了。" | 拆出收入、成本，收入再拆客单价 × 客户数 × 复购率 | 同层混入竞品动作 |
| "帮我拆一下用户流失。" | 每层分解依据统一，叶子可验证 | 只拆一层就下结论 |
| "这些子项哪个优先？" | 用 ICE 排序并说明舍弃项 | 平均用力、全部保留 |
| "先帮我拆，问题还没定。" | 先转 `problem-reframing`，不就地定义 | 边拆边猜问题 |
