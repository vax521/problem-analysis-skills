# 金字塔原理与 SCQA 表达（pyramid_expression）

## 一句话定义

结论先行，自上而下组织论据，让观点被快速理解和接受。

## 何时使用

- 向上汇报、方案评审、商业计划书、演讲。
- 需要说服他人接受一个判断。
- 已有分析结论，需要组织成可读表达。

## 何时不使用

- 探索阶段、结论尚未形成（先完成分析与综合）。
- 纯事实陈述，无需说服。
- 受众需要的是原始数据而非判断。

## 输入

| 参数名 | 类型 | 必填 | 说明 |
|---|---|---|---|
| core_conclusion | string | 是 | 想让人接受的一句话结论 |
| supporting_arguments | list | 是 | 支撑论据 |
| audience | string | 否 | 受众及其关注点 |
| situation | string | 否 | SCQA 中的背景 |

## 输出

- one_sentence_conclusion：一句话结论
- scqa_opening：SCQA 开场（情境–冲突–疑问–回答）
- argument_groups：MECE 分组的支撑论点
- evidence_map：每个论点的证据
- anticipated_objections：预判的反驳与回应

## 执行步骤

按序执行，不可合并或跳步：

1. 写出唯一一句话结论（可被验证或被反驳）。
2. 用 SCQA 构建开场：情境 → 冲突 → 疑问 → 回答。
3. 拆出 3 个左右的支撑论点，检查彼此 MECE。
4. 为每个论点配数据或案例证据。
5. 按受众关注度排列论点顺序。
6. 预判最强反驳并给出回应。
7. 自上而下通读，检查每层是否只回答上一层提出的疑问。

## 判断规则

| 如果 | 则 |
|---|---|
| 论点超过 5 个 | 向上归并一层 |
| 某个论点无法支撑结论 | 删除或改写结论 |
| 读者会先问"所以呢" | 结论必须前置到第一句 |
| 受众是执行层 | 论点后补行动项与责任人 |
| 结论无法被反驳 | 结论过于空泛，重写为可判定的判断 |

## 提问清单

- 一句话结论是什么？能被反驳吗？
- 这 3 个论点是否互相重叠？
- 每个论点的证据在哪？
- 受众最可能反对哪一条？
- 每层是否只回答上一层的问题？

## 常用工具

- 金字塔结构（结论 → 论点 → 证据）
- SCQA 开场
- MECE 分组
- 空–雨–伞（事实 → 判断 → 行动）

## 常见错误

- 按分析时序汇报，把结论放在最后。
- 论点数量过多且互相重叠。
- 有论点无证据，或证据与论点不匹配。
- 忽略受众立场，未预判反驳。
- 把分析过程当成成果交付，决策人看不到行动项。

## 质量检查

输出前逐条核对，未通过的条目标注为待补信息：

- [ ] 第一句话即结论
- [ ] 论点满足 MECE
- [ ] 每个论点有证据
- [ ] 已预判主要反驳
- [ ] 每层只回答上一层提出的疑问

## 正例

输入：分析显示复购率是利润下滑主因。
输出：开场用 SCQA（"上半年利润下滑 12%（情境），主因并非获客（冲突），到底该投获客还是留存（疑问）"），结论"优先投入复购率提升"，配三个 MECE 论点与数据。

## 反例

先讲数据来源、分析过程、中间排除的假设，最后才说结论；读者读到一半仍不知道要做什么。

## 测试案例

| 输入 | 期望行为 | 禁止行为 |
|---|---|---|
| "帮我把这份分析汇报给老板。" | 结论先行 + SCQA + MECE 论点 | 按时序汇报，结论放最后 |
| "论点有 7 条。" | 向上归并至 3 条左右 | 原样罗列 7 条 |
| "结论是'要重视用户体验'。" | 重写为可判定的判断 | 直接沿用空泛结论 |
