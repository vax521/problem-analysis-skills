# 问题定义与重构（problem_reframing）

## 一句话定义

在解决问题前先澄清和重构问题，避免用正确的方法解决错误的问题。

## 何时使用

- 用户直接提出解决方案。
- 多方对问题定义不一致。
- 问题模糊、宽泛、无成功标准。
- 需要判断问题的归属与代价承担者。

## 何时不使用

- 问题已明确定义且只需执行。
- 纯计算或事实查询。
- 已有通过质量检查的问题陈述，用户只需后续分解（转 `mece-decomposition`）。

## 输入

| 参数名 | 类型 | 必填 | 说明 |
|---|---|---|---|
| initial_problem | string | 是 | 用户原始表述，可能含解决方案 |
| stakeholders | list | 否 | 涉及的相关方 |
| current_state | string | 否 | 现状 |
| desired_state | string | 否 | 理想状态 |

## 输出

- problem_statement：重构后的问题陈述
- stakeholder_map：问题归属与相关方诉求
- boundaries：问题边界（含什么、不含什么）
- success_criteria：成功标准
- reframed_questions：重构后的追问

## 执行步骤

按序执行，不可合并或跳步：

1. 澄清"这是谁的问题"。
2. 描述现状与理想状态的差距。
3. 区分问题与解决方案。
4. 追问根源与问题归属。
5. 重构问题陈述。
6. 确认这个问题是否值得解决。

## 判断规则

| 如果 | 则 |
|---|---|
| 用户说"我要做 X" | 追问"X 要解决什么" |
| 责任不清 | 先做利益相关者分析 |
| 问题陈述中包含解决方案 | 剥离方案，重述问题 |
| 无人真正受到损失 | 该问题可能不值得解决，直接指出 |
| 用户拒绝澄清、只要方案 | 给出方案，同时标注"问题未经定义"的风险 |

## 提问清单

- 现状是什么？理想状态是什么？差距在哪？
- 这个问题出现前，发生了什么变化？
- 如果问题永远不解决，谁最难受？
- 这个"问题"是需求、是方案，还是症状？
- 用一句话重述后，还包含任何解决方案部件吗？

## 常用工具

- 现状–理想差距表
- 利益相关者矩阵（诉求 × 影响力）
- TOSCA（Trouble / Owner / Success / Constraints / Actors）
- 5Why 作为定义阶段的探针

## 常见错误

- 把用户说的解决方案当成问题本身。
- 只识别单个利益相关者。
- 成功标准写成"把 X 做好"这类不可检验的表述。
- 边界不声明，导致后续分析无限扩张。
- 在定义阶段就给出方案，污染问题陈述。

## 质量检查

输出前逐条核对，未通过的条目标注为待补信息：

- [ ] 问题陈述不含解决方案
- [ ] 有明确成功标准
- [ ] 已识别主要利益相关者
- [ ] 边界清晰
- [ ] 明确回答"这是谁的问题"

## 正例

输入：用户说"我需要一个更好的 CRM"。
输出：重构为"销售团队跟进效率低，导致线索转化差"，并给出成功标准（线索到商机转化率从 8% 提到 15%）与归属（销售负责人）。

## 反例

输出"建议引入某某 CRM 系统，支持自定义字段与自动化流程"——这是解决方案，不是问题陈述。

## 测试案例

| 输入 | 期望行为 | 禁止行为 |
|---|---|---|
| "我要做个 App。" | 追问"这个 App 要解决谁的什么问题"，产出问题陈述与成功标准 | 直接给功能清单 |
| "团队执行力差。" | 区分"谁的问题"，追问现状、理想、根源 | 直接给激励方案 |
| "我们需要上 ERP。" | 剥离方案，重述为业务问题 | 讨论 ERP 选型 |
| "用户想要更快的马。" | 重构为"更高效地到达目的地" | 讨论养马技术 |
| "帮我算一下 2+2。" | 直接回答，不套框架 | 追问问题归属 |
